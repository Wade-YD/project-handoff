# 为什么是这些规则（防「顺手简化」）

规则本身在 `SKILL.md` 和 `references/templates.md`，这里只记**理由与出处**。删规则前先读这里。

## 可发现性测试 —— `johnpapa/ai-ready`

agent 读代码能自己发现的就别写。**目录树、技术栈、数据模型摘要全部删掉**——它们一个月就过期，且每行都在抢注意力。

留下的四类**不可发现**信息：构建/测试命令（埋在 tooling 配置里）、布局为什么反常、从 review 里挖出的约定、维护矩阵（改了 A 必须同步改 B）。

## 写正面规则 —— `ai-ready` + `mattpocock/skills · writing-for-agents`

写 `Use the v2 client in lib/api/`，不写 `Do not use the v1 client`。**点名废弃的东西会让模型更容易去用它。** 两个独立来源互相印证。

**作用域限定**：这条只管 AGENTS.md 的规则区。HANDOFF 的 Learnings 和 ARCHITECTURE 的 Danger zones **必须点名死路**——它们带原因和替代路径，没有替代方案的禁令才是反模式。

## 150 行天花板 —— `ai-ready`

从 20-30 行起步。经验值是模型遵循约 150-200 条指令后依从性开始衰减，且上下文预算是有限的。**这是经验值，不是精确科学**，但方向对：AGENTS.md 长到读不完就等于没有。

## `file:line` 强制 —— `silkyland/know-my-repo`

写不出引用的 gotcha 就是噪音。真没法引用时写 `observed running <cmd>`，但必须真跑过。

配套的 **`UNVERIFIED` 必须带验证路径**：一个孤零零的 UNVERIFIED 标签、没有验证路径，等于一个沉默的未知。

## 冷启动测试 —— `know-my-repo`

写完文档后只读文档扮成新 agent，回答开头列的问题；答不上就算没写完。**注意**：当前上下文里已经有刚读过的代码，自测无效——必须新开会话或派子智能体。

**必须用读取型子智能体（ZCode 用 `Explore`），且禁止它实跑命令/扫生成目录。** 实测成本差：同一个 ~1.1k 行项目，通用型 agent 烧 409 万 token（它自作主张跑了全部闸门、扫了真实部署目录），`Explore` 只烧 22 万——**省 95%，且结论质量更高**（它不会用「读代码答对」冒充「文档够用」）。

判据补一句：**靠读代码才答上也算失败**。否则子智能体会把「从源码里找到答案」当成通过，给你一个假绿。

## `file:line` 必须回读核对（本 skill 自己踩过的坑）

事故不是引用缺失，是**引用与断言内容不符**：行号引自 `create_junction`，描述却写成「走 shell」（实际主路径不经 shell）。这种错比没引用更危险——它伪装成已核实。

规则：先 Read 该行，再把该行的关键标识符（函数名/常量/文案原文）写进断言；覆写后把全文 `file:line` 抽出来逐条回读一遍。

## HANDOFF 60 行的来历

实测：`skm/HANDOFF.md` 55 行、`sticky-memo/HANDOFF.md` 62 行才装得下真实状态。50 行会砍掉实质内容。统一为 **60 行、`wc -l` 计（含空行）**——不写度量方式，两个人永远吵不出结论。

超限砍序的权威版本在 `templates.md` §三「四条硬规则」第 4 条——此处不复述操作细节，防两处漂移。

## 为什么缺陷要独立放 `docs/backlog.md`（而不是 HANDOFF 的一节）

HANDOFF 的语义是**滚动覆写**——每次会话重写。缺陷往往跨多个会话才修完，写进去必然在下次覆写时被清掉；而「要求模板原样带过来」是靠人肉纪律对抗文件语义，实测会失效。

也不能塞 `Next Steps`：那是有序动作列表，缺陷没有顺序、没有稳定标识、不能去重，混进去会稀释「第一条必须可复制」这条硬规则。

独立文件还顺带解决一个死结：**60 行上限从此有了泄压阀**。

**但独立的 backlog 有个已知失败模式：变成没人读的坟场。** 现场证据：某项目 `docs/backlog.md` 已 776 行、20+ 批次小节、顶部没有状态总览——写了但没人读。所以「顶部只放未闭合区 + 来源必填 + 修完移出压一行 + 只增不减即腐化」不是锦上添花，**是这条规则能否成立的前提**。

## 为什么「门禁要固化」而不建新的动作

某项目 `AGENTS.md` 里本来就有「审查发现落 backlog」的规则，照样没拦住三条 P1 消失——**写在 AGENTS.md 里的规则不会自己触发**，必须绑在「建档」和「收工」这两个必然发生的动作上。

同时明确边界：本 skill 只负责把闸门**固化并执行**，**不负责设计测试体系**。没有自动化测试时，写「`Test: none` + 手工验收命令」并在 backlog 记一条缺口即可——**不要逼 agent 现场发明测试框架**，那是把会话卫生工具变成工程咨询。

## handoff 必须对 git 核实 —— `blader/baton`

写完前跑 `git status --short --branch`。**基于聊天记录写的、自信但错误的 handoff，比没有更糟。**

## 死路是最高价值信息 —— `baton` + `REMvisual/claude-handoff`

两个独立来源都把「已排除的死路」列为最有价值内容：**失败方案是最贵的重发现**。合并成一个时间序的 `What We Tried` + 结论式的 `Learnings & Landmines` 即可，不要两份都留。

## 一个项目一份，滚动覆写 —— `baton`

日期文件会散落成一堆命名不一的交接文档，后来者不知道读哪个。需要历史就用 `git` 管，不用文件名管。**活干完压成 5 行或删**，否则它退化成第二份流水账。

## 明确排除的工具

不是文档生成器，别浪费时间：

- `aider --repo-map`：只在内存里给模型看，**不落盘**
- `repomix` / `code2prompt`：上下文喂料 / 打包器
- `agentrules-architect` 这类多模型流水线：要 API key + 6 阶段，单个本地小项目不划算

## 唯一正面解决「文档腐烂」的设计 —— `cathrynlavery/repo-atlas`

`make atlas-check`：自动生成的部分进 CI 校验，人工部分靠 review。值得借鉴思路，但不必上 10 份文档。

没有 CI 时的替代：HANDOFF 的「最后核实」日期早于最近一次 commit 即视为过期。

## 既有命名优先 —— 命名冲突的代价账

skill 默认名是 `HANDOFF.md`，但很多生态已有别的惯例（工作区 AGENTS.md 规定 `HANDOVER.md`、团队用 `交接文档.md`）。强行改名 = 与已加载的上级规则打架：两条矛盾规则会同时进上下文，每次会话都要重新仲裁。统一命名的收益是「一个入口」，这个收益不依赖具体名字——所以规则正文在 SKILL.md 动作 A 第 0 步，名字听既有约定的。
